## DF-1 -- `mypy` gate reported empty subprocess output as `"ok"`

**Status: IMPLEMENTED / CLOSED.**

### Evidence (from the 2026-08-17 diagnosis at `d856d72`, read-only)

| | |
| --- | --- |
| `mypy` gate executions recorded in `.engine/state.db` | 1560 |
| Rows with `detail = "ok"` | 2 (~0.128%) |
| Legitimate `mypy` failures in the whole history | 0 |

`_run` computed `detail = (result.stdout + result.stderr).strip() or "ok"` and then
discarded `result.returncode`. The `or "ok"` branch is reachable **only** when combined
stdout and stderr are empty, so a stored row of `passed = 0, detail = "ok"` meant *the
subprocess exited non-zero without writing a single byte* -- a process-level failure wearing
a string that reads as success. Because the exit status was never kept, no historical row
could be attributed to a cause (crash vs. OS kill vs. `mypy` internal exit 2).

The two occurrences were run 26 `quality-04-clean` and run 41 `quality-04-broken` --
adjacent positions, different variants, different file bodies, a mirror image across the two
runs, which is the signature of a transient failure rather than a property of either case.
Run 26 `quality-04-clean` was **score-distorting** (the injected `AUTO1-mypy` `HIGH` was the
only blocking defect present). Run 41 `quality-04-broken` was **invalid under the same
infrastructure rule but outcome-neutral** (expected `UNVERIFIED`, over-determined by three
genuine `HIGH` defects). Run 38 `quality-04-clean` was a **separate schema fail-closed
event, not an instance of DF-1**.

### Implementation

`src/engine/verification/automated.py`, in `_run` -- one expression, exactly the fix
prescribed in `DEFERRED_FIXES.md`:

```python
passed = result.returncode == 0
detail = (
    (result.stdout + result.stderr).strip() or f"(no output, exit {result.returncode})"
)
```

- `passed` is untouched. **No verdict semantics moved**, and a genuine gate failure still
  fails closed through `automated_defects()` and `verdict.gate()` exactly as before.
- The fallback is reached only when there is no output to preserve, so **every real gate
  message is preserved byte for byte**.
- Distinct exit codes now produce distinct details, so the next occurrence identifies its
  own cause instead of being unattributable.

### Returncode persistence -- schema finding

`eval_case_automated_gates` is `(id, eval_case_result_id, gate_name, passed, detail,
created_at)`; `verification_results` is likewise returncode-free. **The current schema
cannot persist the exit status in its own column without a DB migration**, and
`.engine/state.db` holds the entire run history with no version-control backup.

A migration is **not strictly necessary**. `detail` is persisted verbatim, so carrying the
exit status inside it is the strongest non-schema diagnostic fix available and is sufficient
to make the anomaly self-diagnosing on first recurrence. No migration was performed. The
production database was opened **read-only** (`file:.engine/state.db?mode=ro`) for schema
inspection and was never written.

## DF-2 -- reconciliation rationale 400-character validation limit

**Status: NOT_APPLICABLE_TO_THIS_REPOSITORY / PROVENANCE_RESOLVED. No production code
change was required, and none was made.**

### Evidence carried in

From Step 6.4R V2: 186 reconciliation responses, 179 accepted, 7 rejected because one or
more rationales exceeded a frozen 400-character validation bound. The 7 were
provider-complete (`end_turn`), not truncation failures; they failed closed and removed
nothing.

### Provenance finding

An exhaustive search of this repository at `f79353c` **and across its entire git history**
found no code the entry could apply to:

- `git grep -i "rationale"` (tracked) -- only `graphify-out/.graphify_analysis.json`, whose
  `*_rationale_*` strings are research-graph node ids generated by `tools/research_graph.py`
  for source comments. Unrelated.
- `git grep -i "reconcil"` (tracked) -- 2 hits, both prose lines *listing DF-2 as deferred*
  (`BENCHMARK_V2_CHANGELOG.md`, `benchmark-v2-implementation-manifest.json`).
- `git log --all -S"rationale"` and `-S"reconcil"` -- `f79353c` only, i.e. those same prose
  lines. **No commit has ever added such code.**
- `git grep "\b400\b"` -- HTTP status codes in `src/engine/api.py`,
  `BENCHMARK_MAX_TOKENS = 400_000`, an Anthropic 400-response comment. No character bound.
- `git grep -E "len\([^)]*\)\s*[<>]"` and `git grep -E "\[:\s*[0-9]+\]"` over `*.py` -- no
  string-length validation anywhere; the only truncations are `detail[:2000]` and
  `commit_sha[:7]`.
- No 2400-token response budget exists; judge lens calls use `max_tokens=800`
  (`JUDGE_MAX_OUTPUT_TOKENS`).
- `.engine/state.db` (read-only) has no reconciliation table.

**This does not claim the Step 6.4R issue was unreal.** The 7-of-186 evidence stands as
recorded. The finding is about location only: the implementation imposing that bound lived
**outside this repository**, in the exploratory Step 6.4R tooling, and is not part of the
current engine codebase. DF-2 is an experiment-local issue, not a pending
production-repository infrastructure defect.

Building a reconciliation validator here purely so a limit inside it could be relaxed would
have fabricated infrastructure for a use case this codebase does not have -- forbidden by
`CLAUDE.md`'s *Simplicity first* and *Surgical changes* rules, and a widening of the
measured surface immediately before the first clean Benchmark v2 baseline. If reconciliation
tooling is ever brought into this repository, the bound must be reconsidered at that point
against the then-current response budget and the stored V2 evidence -- never against a
benchmark score.

## Remaining infrastructure risks

1. **The DF-1 root cause is still unidentified.** The fix makes the anomaly self-reporting;
   it does not prevent it. A silent subprocess death remains possible and will still fail
   the gate closed -- correctly -- but will now name its exit code. Historical rows stay
   unattributable, because the information was never written.
2. **Exit status is carried in free text, not a column.** Querying it means string-matching
   `detail`. A dedicated column remains available as a separately-approved migration if a
   future recurrence makes it worthwhile.
3. **Arm boundary.** `automated.py` is inside `src/`, so this commit ends the Phase 5A arm's
   configuration. **Do not pool runs across it.** Everything after this commit is a new arm.
4. **DF-2 is resolved by provenance, not by test.** If reconciliation tooling is later
   imported into this repository, it will arrive with the 400-character bound unexamined in
   this codebase and must be reviewed then.
